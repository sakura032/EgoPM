# EgoPM-Bench 项目背景与本阶段任务叙事

## 一、项目要研究什么

EgoPM-Bench 是一个面向第一人称长期记忆与未来提醒决策的评测数据集。它研究的不是“模型能否概括视频”，而是：当个人生活记录持续到来时，模型能否识别与提醒条件直接相关的可观察证据，在正确时机触发或保持沉默，并给出可追溯的证据。

完整数据链分为五层：

1. **Source Atom**：从第一人称字幕与稠密描述中切出的、只读且可追溯的最小观察单元；
2. **Cue**：单个 Atom 内可以从原字段直接取证的观察事实；
3. **Seed**：一项独立提醒任务，引用一个 trigger Cue，并配置同 split 的困难 lure；
4. **Life Log**：由 Seed 派生的正负分支和不同难度事件序列；
5. **Decision/Evidence**：状态机给出的触发决策与金标准证据。

本目录只承担第 1 层到第 2 层之间的**候选筛选**。它不能越权生成后续层内容。

## 二、为什么要先做 BGE-M3 筛选

Source 共 370,799 条。直接把全部 Source 交给生成式 API 会增加成本、恢复复杂度和无效调用比例，也不利于控制参与者、模态、split 与来源组覆盖。

此前的 Cue 生产暴露出明显语义质量问题：大量结果把几乎所有事实错误归为 `time`，若干字段长期为空，predicate 出现哨兵字符串，甚至出现人物名称进入时间槽位。这说明仅靠结构化 JSON 校验和大规模生成不能保证语义质量。

新的生产方向是：

```text
370,799 条冻结 Source Atom
        ↓ 固定 BGE-M3 dense+sparse 召回、确定性过滤、分层多样性筛选
8,000–12,000 个候选 Atom
        ↓ 单一固定生成模型抽取 Cue v2，并执行逐 clause 证据与语义门禁
约 3,000–5,000 条高质量 accepted Cue
        ↓ 检索、规则过滤和多样性采样
900–1,400 个 Seed candidates
        ↓ 机器审计与人工终审
480 个 Frozen Seed
        ↓ 每个 Seed 生成 2 个分支 × 3 种难度
预计 2,880 条 Life Log
```

BGE-M3 的作用是提高下一阶段的有效密度和语义多样性，而不是证明某个 Atom 必然包含合格 Cue。最终 Cue 是否接受，仍由原字段证据、Schema 和语义门禁决定。

## 三、关键术语

- `Source Atom`：`input/source_video_atoms.jsonl` 中的一行，只读。
- `passage`：仅为 BGE-M3 编码构造的派生文本，不是新的 Source。
- `selection`：一次由固定 Source、固定模型 revision、固定参数和固定查询集共同定义的候选筛选快照。
- `selection_id`：该快照的唯一身份；任何身份参数变化都必须创建新 ID。
- `query family`：围绕一种可观察事实设计的一组冻结检索查询。
- `dense`：BGE-M3 稠密向量召回通道。
- `sparse`：BGE-M3 稀疏词项权重召回通道。
- `RRF`：只使用名次、按冻结常数融合不同召回列表的 Reciprocal Rank Fusion。
- `diversity reservoir`：用于降低高频场景支配、补充语义簇和来源覆盖的候选池。
- `manifest`：绑定文件相对路径、SHA256、行数、字节数和上游身份的机器可读清单。
- `SUCCESS`：全部门禁通过后由唯一协调器最后写出的阶段完成标记；它不是普通运行日志。

## 四、Source Atom 本地字段合同

正式输入每行是一个 JSON 对象，必须包含以下与本任务直接相关的字段：

| 字段 | 含义 | 本阶段用途 |
| --- | --- | --- |
| `atom_id` | 全局唯一 Atom ID | 候选主键与确定性排序键 |
| `atom_kind` | 固定为 `source_video_atom` | 输入身份校验 |
| `atom_stage` | 固定为 `final` | 输入冻结状态校验 |
| `participant_source_id` | 参与者来源 ID | 分层与分布报告，不进入 passage |
| `source_day` | `DAY1`–`DAY7` | 分布诊断，不进入 passage |
| `session_id` | 会话 ID | 回查与诊断，不进入 passage |
| `source_group_id` | 来源组 ID | 防止单一场景支配，不进入 passage |
| `transcript` | 对话转写，可为字符串或空值 | passage 第一字段 |
| `dense_caption` | 稠密画面描述，可为字符串或空值 | passage 第二字段 |
| `visible_text` | 可见文本，非空字符串 | passage 第三字段 |
| `modality_coverage` | `transcript_only`、`dense_caption_only` 或 `both` | 分层与报告，不进入 passage |
| `split` | `train`、`dev` 或 `test` | 分层与报告，不进入 passage |
| `provenance` | 固定为 `egolife_srt` | 来源身份校验 |

输入还可能包含时间、片段 ID、只读来源路径和视频映射状态。它们必须原样保留在 Source 中，但不得写入 passage，也不得复制进正式候选 JSONL。

## 五、什么样的 Atom 对后续 Cue 有价值

优先召回能支持以下**直接可观察事实**的 Atom：

- 人物出现、相遇、交谈、递交或共同活动；
- 进入、离开或处于可辨识地点；
- 物体出现、持有、拿取、放置、开启、关闭或状态改变；
- 活动开始、持续、结束或明确完成；
- 环境、设备、食物、门窗等发生可观察状态变化；
- 原文中明确出现时间、频率、期限或先后关系。

以下内容不是本阶段的目标：

- 由常识推断但原字段没有直接证据的事实；
- 跨多个 Atom 才能拼出的关系；
- “未来某时提醒我”这类虚拟时间；
- 具体 Seed 的 trigger/lure 答案；
- 参与者 ID、split、路径或时间戳等元数据捷径。

## 六、科学严谨性的含义

本阶段的质量不由单一相似度阈值决定，而由以下可审计属性共同保证：

- **身份冻结**：Source、模型 revision、参数、查询集与随机种子均被哈希绑定；
- **可复算**：相同输入和参数应得到相同候选及顺序；
- **高召回**：多查询族、dense、sparse 与融合通道共同降低漏召；
- **多样性**：限制同一参与者、模态、来源组和语义簇支配结果；
- **无泄漏**：passage 不包含 split、参与者、路径、未来标签或后续任务答案；
- **可追溯**：正式候选只引用真实 `atom_id`，每个命中可追到查询与检索通道；
- **不越权**：BGE-M3 分数不被解释成 Cue 正确性或最终标签。

## 七、WSL Codex 的具体使命

WSL Codex 应把自己视为一个受合同约束的本地检索工程师，而不是通用数据清洗代理。它需要：

1. 验证三项本地输入和冻结身份；
2. 建立可复现的 GPU 环境并固定模型文件；
3. 实现流式输入、分片 embedding、恢复和完整性校验；
4. 严格执行冻结查询、融合、多样性与分层策略；
5. 输出不含 Source 正文的候选 ID 和完整分布报告；
6. 证明没有重复、越界、身份漂移或静默降级；
7. 只有全部门通过后写 SUCCESS，并把整个输出目录交给用户。

如果本目录没有提供足够信息完成其中任何一步，应生成缺口报告并停止，而不是自行推断主项目意图。
